# 2.4.0 gate closure checklist

Status: working checklist. The maintainer explicitly approved the 2.4.0 release on 2026-11-14
with these external gates still open; that release decision does not mark the gates complete.
This document itself does not close any gate. The verified release source is `4dc484a`; the
final documentation sync is `42c6b80`. Both have green Verification, Publishing, Instrumentation
and Tablet runs.

Existing evidence does not close the three external gates below:

- the API 29 emulator is a phone smoke test, not a real-device, foldable or accessibility run;
- the benchmark is a JVM reporting harness, not target-hardware acceptance;
- the OSV findings are in the AGP buildscript and need a maintainer decision or an AGP upgrade.

Close a gate only by attaching the evidence named here, marking the corresponding boxes and
updating [CHINESE_CALENDAR_QUALITY.md](../CHINESE_CALENDAR_QUALITY.md) and
[2.4.0.md](2.4.0.md). A missing device, measurement or owner/expiry is an open blocker.

## Gate A - real devices, fold, TalkBack, large font and RTL

### A1. Required testbeds

The documented matrix requires at least a real phone, a real tablet and a real foldable. Record
the exact model, build fingerprint, Android/API level, ABI, locale and font scale for each run.
An emulator can add evidence but cannot replace any of these rows.

| ID | Testbed | Minimum coverage | Evidence | Status | Can the maintainer supply it? |
|---|---|---|---|---|---|
| A1 | Real phone | Portrait and landscape | Screenshots/video, device fingerprint, pass/fail notes | Open | Yes: device access or recorded run |
| A2 | Real tablet | Portrait and landscape, multiple columns, split-screen | Screenshots/video, width/density, pass/fail notes | Open | Yes: device access or recorded run |
| A3 | Real foldable | Book and tabletop postures, hinge behaviour | Photos/screenshots/video in both postures, model/fingerprint | Open | Yes: foldable access or recorded run |
| A4 | Accessibility test device | TalkBack enabled, Chinese and English labels | TalkBack version, spoken transcript/video, focus-order notes | Open | Yes: device with TalkBack and a tester |
| A5 | Large-font/RTL device | Font scale 200%, Arabic or Hebrew locale/RTL | Settings values, before/after screenshots, pass/fail notes | Open | Yes: device access or recorded run |

If the release continues to advertise `minSdk 27`, add an explicit API 27 run or state that API 27
was not tested. Do not imply coverage that was not executed.

### A2. Common product path on every testbed

Use the APK built from the verified source (or a later reviewed source commit) and record its
SHA-256. On each device:

- [ ] Launch the sample and open the compact `CN 2.4.0` entry.
- [ ] Confirm the title `2023 Leap 2nd Month` and details `Epoch day: 19445`,
  `Gregorian: 2023-03-29`, `Leap month: yes (month 2)` and
  `Chinese: 2023 Leap 2nd Month, day 8`.
- [ ] Inspect `Chinese labels` in English, Simplified Chinese, Traditional Chinese and numeric
  (`1/2`) styles; no missing, clipped or incorrectly marked leap-month labels.
- [ ] Enable `Gregorian grid + Chinese labels`; confirm the Gregorian title/navigation remains
  Gregorian while Chinese secondary labels and leap-month names are visible.
- [ ] Exercise None, Single, Multiple and Range selection; confirm epoch-day identity and
  selection survive calendar switching, rotation and activity recreation.
- [ ] Exercise disabled days and markers where the sample exposes them; confirm they remain
  distinguishable and do not corrupt selection or accessibility labels.
- [ ] Navigate regular month -> leap month -> following month, across a year boundary and at
  both supported engine bounds; no invented leap month and no blank supported day.
- [ ] Enable Previous/Next month days, fixed six rows, week numbers and agenda where applicable;
  no overlapping, clipped or duplicated cells.
- [ ] Open the 13-month heatmap for 2023 and a 12-month year; both render and remain usable.
- [ ] Record every deviation as a finding with device, locale, font scale, steps and screenshot.

### A3. Phone, tablet and continuous layout

- [ ] Phone portrait and landscape: no clipped title, weekday row, day cell or details block.
- [ ] Tablet portrait and landscape: multiple columns remain readable; no stretched or clipped
  month grid.
- [ ] Split-screen and continuous width changes: controls and calendar reflow without losing the
  selected/visible month.
- [ ] Record screen size in pixels and dp, density, orientation and multi-window state.

### A4. Foldable postures

- [ ] Book posture: content is not split through a day cell; controls are not under the hinge.
- [ ] Tabletop posture: calendar and controls remain reachable; no hidden or duplicated content.
- [ ] Fold/unfold during navigation preserves the settled month and selection.
- [ ] Synthetic `sampleLocalFold` tests are not accepted as evidence for this row.

### A5. TalkBack

- [ ] Enable TalkBack and record its exact version.
- [ ] English labels: each day exposes its Chinese date plus the Gregorian ISO date in the
  accessibility label.
- [ ] Chinese labels: simplified/traditional month and day labels are spoken correctly.
- [ ] Leap month: the title and day accessibility text retain the leap marker (`M2L` or `闰` as
  applicable); no silent loss of `isLeapMonth`.
- [ ] Check selection, today, disabled days, markers and range endpoints through TalkBack.
- [ ] Check focus order in the grid and that focus is not trapped by the compact demo entry.
- [ ] Record a spoken transcript or short video; a screenshot alone does not prove speech output.

The implementation currently composes Chinese day accessibility labels as
`ChineseFormat.dateLabel(...) + " (" + ISO date + ")"`; verify the actual spoken output rather
than assuming it.

### A6. Large font

- [ ] Set Android font scale to at least 200%; restart the app so the change is applied.
- [ ] Repeat the common path and both grids; no clipped title, day label, details line or
  inaccessible control.
- [ ] Record the exact scale, e.g. from `adb shell settings get system font_scale`.
- [ ] Restore the original scale after the run.

Example commands for a connected device:

```bash
adb shell settings get system font_scale
adb shell settings put system font_scale 2.0
# force-stop and relaunch the sample, capture screenshots
adb shell settings put system font_scale 1.0
```

### A7. RTL

- [ ] Test both LTR and RTL; use the sample's `ar` locale together with its `RTL` switch, and
  additionally a device-wide Arabic/Hebrew locale if available.
- [ ] Check reading direction, weekday order, navigation arrows, controls and details.
- [ ] Confirm no clipped labels, inverted day order or lost selection after toggling RTL.
- [ ] Record locale tag, layout direction and screenshots for both states.

### A8. Touch targets

- [ ] Measure the bounds of month navigation, calendar/mode chips, switches and day cells with
  Layout Inspector or `uiautomator dump`; record the measured dp values.
- [ ] Specifically measure the compact `CN 2.4.0` entry. Its visual pill is intentionally small;
  do not claim a 48 dp target without measuring it.
- [ ] If a control is below the project's accepted minimum, record it as a finding before closing
  this gate rather than claiming blanket compliance.

Example bounds collection:

```bash
adb shell uiautomator dump /sdcard/window.xml
adb pull /sdcard/window.xml artifacts/device/window.xml
```

## Gate B - target-hardware measurement

### B1. Name the target first

The current JVM baseline is not target-hardware acceptance. Before measuring, the maintainer must
name the target and its scope:

- [ ] Device or host model, SoC/CPU, RAM, ABI and OS/API.
- [ ] Build type (release vs debug), app version/commit and APK SHA-256.
- [ ] Thermal/power state and whether the run is cold or warm.
- [ ] For a JVM-only claim: JDK vendor/version, VM, heap and CPU count.
- [ ] Whether the target is a physical Android device, a representative host, or both.

### B2. Choose one measurable acceptance path

The repository currently contains only `ChineseJvmBenchmarkTest`, a JVM reporting harness. It has
no Android benchmark or macrobenchmark test. Therefore:

- **B2a - JVM host acceptance:** run the existing harness on the named host hardware and record
  its four operations. This can support a JVM-only claim, not a physical Android-device claim.
- **B2b - physical-device acceptance:** requires an on-device benchmark harness (engine
  operations plus the relevant Compose/month rendering path). Adding such a harness is new code
  and possibly a new dependency; it needs separate approval and must not be smuggled into this
  release as a checklist-only change.

Do not mark B2b complete from a JVM run or from the API 29 software emulator.

### B3. Measurements required

For every operation below, record median of five measured samples after two warm-up runs, the raw
sample times, allocations where available, and the data-set size:

| Operation | Data set | Current provisional budget |
|---|---|---:|
| Epoch day -> Chinese -> epoch day | 72,674 days | <= 1,000 ns/op, <= 512 B/op |
| `chineseMonthData` month construction | 2,461 months | <= 100,000 ns/month, <= 100 KB/month |
| 13-month heatmap (`chineseYearHeatmap(2023)`) | 13 months | <= 5 ms/year, <= 1.5 MB/year |
| Repeated `next`/`previous` navigation | 100,000 steps | <= 1,000 ns/step, <= 512 B/step |

Also record artifact sizes as in the current baseline (engine metadata/JVM/linuxX64 and Compose
AAR) and any device-specific memory pressure or jank observed during the UI path.

```bash
./gradlew :calendar-chinese-compose:testDebugUnitTest --tests '*ChineseJvmBenchmarkTest*'
```

### B4. Acceptance decision

- [ ] Compare measurements with the provisional budgets; do not silently relax a budget.
- [ ] Record whether each budget is accepted, adjusted with justification, or rejected.
- [ ] If adjusted, record the reason, owner and resulting release budget.
- [ ] Attach the raw `BENCHMARK` output and the exact hardware description.
- [ ] State explicitly whether the result supports JVM-only or physical-device acceptance.

### C2. Required acceptance fields

If the maintainer chooses acceptance instead of an AGP upgrade, provide every field:

- [ ] Maintainer/owner (name or GitHub handle) who accepts the risk.
- [ ] ISO expiry date; no open-ended acceptance.
- [ ] Per-finding severity and the applicable Critical/High or Medium/Low policy.
- [ ] Scope confirmation: buildscript-only, not shipped at runtime.
- [ ] Justification: why the exposure is acceptable for this release.
- [ ] Compensating controls: isolated build environment, no untrusted build scripts, network
  restrictions, credential scope, or other concrete measures.
- [ ] Re-scan or review trigger: AGP upgrade, expiry, new advisory or changed build graph.
- [ ] AGP upgrade tracking issue/owner if acceptance is temporary.
- [ ] Approval date and signature/comment location.

The acceptance is a maintainer decision. The implementation workflow must not invent an owner,
expiry or justification.

### C3. If acceptance is not granted

An AGP upgrade is the alternative. That is a separate version/toolchain change and is explicitly
outside this checklist task. Do not change versions, suppress findings or silently exclude the
buildscript graph.

## Execution order

1. Maintainer supplies device access, named hardware and/or advisory decision.
2. Run Gate A on the exact source/APK; attach evidence and file findings.
3. Run Gate B on the named target; accept or adjust budgets with an owner.
4. Complete or reject Gate C; rerun the OSV scan on the final source.
5. Update [CHINESE_CALENDAR_QUALITY.md](../CHINESE_CALENDAR_QUALITY.md),
   [2.4.0.md](2.4.0.md) and the release plan with the evidence.
6. Re-run the four remote workflows on the resulting documentation commit.
7. Request separate explicit merge/tag approval. JitPack 2.4.0 remains blocked until a tag exists.

## Definition of done for this checklist

- [ ] Every A1-A9 row has named evidence and a pass/fail result.
- [ ] Every B3 measurement has a target, raw output, median, budget decision and owner.
- [ ] Every C1 finding has an owner/expiry acceptance or a completed AGP upgrade.
- [ ] The runtime OSV scan is green on the final source.
- [ ] The quality document and release notes no longer list these gates as open.
- [ ] All four workflows are green on the verified source.
- [ ] Merge/tag approval is obtained separately; no tag or publication exists before that point.
