## What is new

Own Kotlin engine `:calendar-chinese-native` and optional Compose integration
`:calendar-chinese-compose`: leap months, bidirectional epoch-day conversion, navigation,
saved state, month/week data, heatmaps and playground integration. No foreign calendar engine,
no ICU wrapper, and no HKO table in the artifact.

Supported Chinese years are `1901..2099` (Gregorian `1901-02-19..2100-02-08`, 72,674 days,
2,461 months, 73 leap years). The engine runs on `jvm()` and `linuxX64()`; iOS targets are
deliberately not declared while no macOS runtime check exists. The Compose facade remains
Android because `:library` is Android-specific.

## Data provenance

`tools/chinese-calendar/generate.py` generates the month table at development time from the
VSOP87D Earth series, Meeus chapters 25/49 and the Espenak-Meeus Delta-T. HKO tables served only
as a development comparison: **2,458 exact + 3 audited differences = 2,461 month starts,
0 missing references/files**; for the three differences 1914-11-18, 1916-02-04 and 1920-11-11,
`tools/chinese-calendar/reference-conflicts.json` documents the complete time-chain step:
JDE (TT), Delta-T, UTC, UTC+8 calendar date and a structured independent NASA/GSFC reference
with source, URL, UTC time and a 60 s tolerance. The NASA table gives 1914-11-17 16:02 UT,
1916-02-03 16:05 UT and 1920-11-10 16:05 UT. The calculated new moons occur 1m43s, 5m16s and
4m50s after UTC+8 midnight; the HKO row names the preceding UT calendar day. This is consistent
with Beijing local time (UT+7:45:40) before 1929. The library deliberately remains on the
modern UTC+8 convention and does not adopt a historical local-time rule; a blanket switch would,
according to the audit, also move other month starts (for example 1906-04-24). The table
therefore remains on the documented UTC+8 date, without an HKO correction. `--verify-reference`
checks reference files, all month starts, year and leap-month assignment, equality of the UTC
and UTC+8 instant, explicit time zones and the NASA time within the documented tolerance; it
fails on undocumented differences. No HKO data or ICU/lunar-java code is copied or shipped.

## Error handling and rollback plan

Before tagging: stop the release, fix the issue and repeat all affected gates on the new commit.
After tagging: never overwrite the tag/artifacts; document failures openly and plan/approve a
2.4.1 patch separately. Consumers can fall back to 2.3.0 without the new modules; there is no
automatic backward migration.
