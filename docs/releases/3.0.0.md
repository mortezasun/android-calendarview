# 3.0.0 – Kotlin Multiplatform calendar (2026-11-16)

`3.0.0` is the first Kotlin Multiplatform release of `android-calendarview`. The Compose calendar
core and the Gregorian, Hijri, Solar Hijri and Chinese lunisolar engines now build from
`commonMain` for Android, the JVM and iOS. The release was cut from the `kmp` line; the older
Android-only `2.4.0` line was previously on `master` and has since been fast-forwarded to this
tree.

## Highlights

- `:library` and the calendar modules publish Android AARs, JVM jars and iOS klibs from one
  source tree.
- Immutable calendar value types (`GregorianYearMonth`, `HijriDate`, `SolarHijriDate`,
  `ChineseMonth`/`ChineseDate`) use epoch-day identity; platform hooks supply locale formatting,
  first day of week, digits and "today".
- `:calendar-solarHijri` is a facade over the dependency-free `:calendar-solarHijri-native`
  engine. `ir.huri:jalalicalendar` is no longer declared or published.
- The JVM API guard is joined by a KLIB ABI snapshot guard for the iOS surface.
- Additional property tests cover date round-trips, leap months and month boundaries; an
  accessibility test covers day descriptions, RTL and a 200% font scale.

## Breaking changes from 2.4.0

- Callbacks and predicates take an epoch day (`Long`); `firstDayOfWeek` is ISO 1..7 and
  `todayEpochDay` replaces `today`.
- `YearMonth` becomes `GregorianYearMonth`, `HijrahDate` becomes `HijriDate` and
  `JalaliCalendar` becomes `SolarHijriDate`.
- `Locale` parameters are removed; labels come from the platform formatter.
- The `@Deprecated(HIDDEN)` `java.time` overloads are removed. JVM/Android hosts can convert at
  the boundary with `SolarHijriDate.toLocalDate()` and the `HijriDateProvider` mappings.

See [ADR 0006](../decisions/0006-kotlin-multiplatform-calendar-modules.md) and the README
migration section for the complete mapping.

## Post-release tooling (branch `kmp`, no new tag)

Dokka `2.3.0` now generates HTML for all seven published modules into `build/dokka/html`; the
`API documentation` workflow uploads the artifact and deploys it when Pages uses workflow builds.
The separate `:benchmarks` module uses kotlinx-benchmark `0.5.0` for Gregorian/Hijri month
calculations and the shared heatmap adapters; it is not part of `check`, `build` or CI. The Gradle
wrapper is on `9.9.1`, and the local gate stack passes on it. The post-release work also adds two
Kotlin/Native tests, so the current branch has 16 while the tagged `3.0.0` release had 14. See
[BENCHMARKS.md](../BENCHMARKS.md) and [PROJECT_STATUS.md](../PROJECT_STATUS.md) for the current
tooling evidence.

## Known limitations

- iOS runtime and simulator tests, linking a framework into an iOS app and an `iosApp` sample
  require macOS/Xcode and were not executed. The published iOS klibs are file- and ABI-checked.
- Real process-death tests and physical-device/fold/TalkBack acceptance still need dedicated
  hardware or a stable emulator harness; API 29 emulators are not a full device matrix.
- JitPack remains the configured remote repository. Maven Central signing, namespace
  verification and upload credentials are not configured.
